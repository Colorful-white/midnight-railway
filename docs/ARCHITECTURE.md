# 当前代码结构与后续维护方向

本页描述实际实现。末尾的框架整理是规划，不是现存 API。

## 运行时结构

| 文件 | 当前职责与入口 |
| --- | --- |
| `index.html` | 页面、菜单、封面 SVG、图标和脚本入口；脚本按顺序 `defer` 执行 |
| `railway.css` | 页面布局、车窗框、左侧控制、响应式和封面 |
| `launch.js` | `window.RailwayLaunch`；加载里程碑、首帧完成、前台重入、失败提示 |
| `app-install.js` | 平台安装说明、离线准备状态、检查与应用更新 |
| `world.js` | 全局词法常量 `RailwayWorld`；闭合线路、时刻插值、地形、地物、轨道和车体网格 |
| `mint-sea.js` | `MintSea`；薄荷海静态网格、鱼群、鳐鱼和场景影响范围 |
| `cabin.js` | `CabinScene`；窗台、花、合书、茶杯及动态热气 |
| `railway.js` | UI 行为、时间、镜头、光照、WebGL 着色器、缓冲与动画帧 |
| `manifest.webmanifest` | PWA 身份、名称、启动路径、显示方式、图标 |
| `sw.js` | 内容版本化的离线缓存模板与主动应用更新 |
| `build.mjs` | Node.js 构建；白名单复制源文件并替换 SW 版本 |
| `.github/workflows/pages.yml` | `main` 推送后构建和部署 GitHub Pages |

脚本顺序：`launch.js → app-install.js → world.js → mint-sea.js → cabin.js → railway.js`。虽然安装脚本较早执行，所有 `defer` 脚本都在 DOM 解析后执行。`world.js` 必须早于两个景观/前景模块；这些模块必须早于主渲染器。

没有模块打包器；`RailwayWorld`、`MintSea`、`CabinScene` 是脚本之间共享的顶层词法绑定，不应假设它们等同于 `window` 属性。

## 时间、线路与地形

`railway.js` 的 `localMinute()` 使用设备的本地时分秒。`activeMinute()` 在实况、时段体验和暂停之间切换。`motionSeconds` 用于动效，与所选日内时刻分开。

`world.js` 从控制点生成 Catmull–Rom 闭合轨道与里程表：

- `distanceAt(minute)`：将日内时刻插值成线路里程。
- `position(distance)`：按里程返回三维位置；`heading(distance)` 返回水平朝向。
- `stops` 和 `timeline`：时刻与景观窗口；`chapters` 是地理章节，数量不同于景观站点数。
- `featureShots`：分段俯视模式靠近景观时的镜头目标与距离。
- `groundHeight(x,z)`：地形高度；`terrain` 字段是核心地形网格数据，两者不要混淆。

坐标为 Y 向上。车与鱼的模型局部正 X 为前方。当前列车绘制主要按水平朝向旋转，坡道上的完整车体俯仰还不是通用能力。

线路变长会影响时间到里程的映射。设计新景观时同时考虑入口、出口、相切连接、爬升、地形约束、车厢间距与观景速度。薄荷海使用局部相切曲线接入圆形观景线路，上层出口与下层长廊分离。

## 网格与绘制

`RailwayWorld.Mesh` 的每顶点布局为 **10 个浮点数**：位置 3、法线 3、颜色 3、发光/透明标记 1。全局着色器通过这个布局处理不透明物体、半透明网格、车灯和蒸汽粒子。

当前约定包括：普通网格的发光标记非负；低于 `-1.5` 的标记进入半透明分支，透明度从 `-emission - 2` 得到。其他负值还有水面等专门语义。增加材质前阅读着色器，不能随意复用标记。

`railway.js` 按需缓存周围地形、地物和轨道段；缓冲淘汰时删除 GPU 资源。薄荷海静态场景懒初始化，鱼体/尾鳍复用七种颜色的模型；鳐鱼与茶的热气复用动态数组和 GPU 存储。

绘制大致顺序：世界地形与轨道 → 近处景观与动物 → 俯视列车 → 半透明景观 → 车窗前景。前景使用单独的深度通道和较紧的近远裁剪面。

动画循环的帧间隔门限是 30ms，渲染分辨率的 DPR 上限是 1.6。这不是对任何手机实际帧率的保证。

## 薄荷海的现有耦合点

这还不是“放一个配置就能生成新景观”的框架：

1. `world.js` 的 `sea` 定义位置与水位，`stops[3]`、地形盆地、路线插入和时间节点直接关联。
2. `MintSea` 直接读取 `W.stops[3]`，由 `routeStart/routeEnd` 生成长廊、避开轨道的珊瑚和鱼群分布。
3. `railway.js` 的 `prepareSea()`、动物绘制、半透明层、水下光照和着色器对薄荷海有专用分支。
4. 入口还涉及脚本顺序、构建白名单和 SW 缓存白名单。

新增或调整站点时不能只改数组中的时刻，也不能任意调换 `stops` 顺序后假设薄荷海仍能正常引用。

## 光斑精度与更新机制

海底光纹曾使用较大的日内时间数值，在模拟半精度下出现大量重复帧。当前与日内时刻解耦：高精度路径使用有界角度，低精度路径使用 CPU 计算的正弦/余弦单位相位。亮边经过平滑处理，暂停和减少动态效果仍有效。

PWA 构建对运行时白名单文件及 `sw.js` 模板计算内容散列。SW 安装完整缓存；旧版继续观景，准备完成后由用户点击更新。查询参数会被 SW 去掉后再匹配缓存，因此 `?v=...` 不是可靠的旧缓存绕过方式。

## 后续框架整理建议：尚未实施

长期可以逐步把站点 ID、时刻、观景窗口、路线入口、镜头、静态网格和动画入口组织成统一景观定义，先迁移一个现有景观验证等价，再接入新的景观。

这应以保持已发布效果为前提，分小步处理：先减少按 `stops[3]` 这类位置索引引用，再收拢专用渲染入口，最后补可重复的回归检查。当前不存在 `SceneRegistry`、通用景观插件 API、统一场景编辑器或持续运行的自动化测试套件。

更换模型只影响开发协作，不要求更换引擎、网址或工程。后续需要较大技术改造时，先界定具体收益和影响范围。
